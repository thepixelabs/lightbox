# Cloud sync and the product ecosystem (Lightroom cloud vs Classic, mobile/web/TV clients, sharing & collaboration, Sensei AI services, community, extensibility & APIs)

Adobe ships two distinct products under the Lightroom name. Lightroom Classic is a desktop-first, catalog-centric application: photos live in the user's own folders, the catalog is a local SQLite database, and cloud connectivity is an optional bolt-on. The cloud-based Lightroom (desktop, iOS, Android, web, Apple TV) inverts that model: the cloud copy of every full-resolution original is the source of truth, local storage is treated as a cache, and every client renders the same parametric, non-destructive edit recipe. The two worlds bridge asymmetrically — Classic uploads only ~2560px lossy-DNG "Smart Previews" of synced collections (which don't count against storage quota) while downloading full originals that arrive from cloud clients — and a one-way migration tool converts a Classic catalog into a cloud library. Notably, the cloud desktop app recently gained a "Local" mode that browses and edits files in place, writing edits to XMP sidecars without any upload, signaling Adobe's convergence toward a hybrid local/cloud model — exactly the architecture an open-source clone should target (local-first, with optional self-hosted sync a la Immich or PhotoPrism).

The ecosystem's stickiness comes from services layered on top of sync. Adobe Sensei runs server-side ML that makes unkeyworded libraries searchable by content, clusters faces into a People view, auto-picks the "best" photos of an album, and powers adaptive presets that pre-mask skies, subjects, and portraits. Sharing is deeply built in: albums can be published as themed web galleries via link or QR code, or restricted to invited members with tiered permissions (view / contribute / edit), with likes, comments, and a notification bell enabling client-review workflows. A social layer ("Community", formerly Discover) lets users publish edits as step-by-step replays others can watch and save as presets, mark photos as remixable, follow photographers, and consume interactive in-app tutorials; subscription-gated Premium and Adaptive preset packs round out the content offering. Versions (manual "named" snapshots plus automatic rollback points) sync across devices, and Creative Cloud integration provides Edit-in-Photoshop round-tripping and pooled storage plans.

Extensibility differs sharply between the products. Classic has a mature Lua SDK — plugins declare themselves via an Info.lua manifest and can add export/publish destinations, metadata fields, library menu commands, dialogs, and web gallery engines — which spawned a large third-party economy (Any Vision for LLM/Vision-API keywording, Negative Lab Pro for film-negative inversion, LR/Mogrify for export decoration, jf publish plugins, Excire for local AI search). The cloud Lightroom has essentially no plugin support; instead Adobe exposes a partner REST API at lr.adobe.io (OAuth via Adobe IMS) with endpoints for catalogs, assets, albums, uploads, and renditions, which powers integrations like camera-vendor auto-upload and Firefly services. For Lightbox v1 (desktop), the must-haves in this domain are local-first browsing with XMP sidecars, versions/snapshots, and external-editor round-trip; the highest-leverage differentiators are locally run CLIP search and face clustering (proven feasible by Immich); and the sync service, mobile/web clients, and social features are deferrable but should shape the data model (edit recipes as serializable, orderable operations) from day one.

## Feature inventory

| Feature | Priority | Complexity | Description | Building blocks |
|---|---|---|---|---|
| **Cross-device edit and metadata sync** | could | very-high | Non-destructive edit recipes, ratings, flags, keywords, and album membership propagate automatically to every signed-in device, with offline changes queued and reconciled when connectivity returns. All clients render the identical parametric edit so a photo looks the same everywhere. | Automerge or Yjs (CRDTs for conflict-free edit-state merge), CouchDB/PouchDB replication protocol, SQLite + Litestream, gRPC/WebSocket transport |
| **Full-resolution original storage in the cloud** | wont | very-high | Cloud-native clients upload the untouched original (raw included) to server storage, which becomes the source of truth; plans are tiered by quota (e.g. 20GB / 1TB and up) with usage metering in-app. | MinIO / Garage / SeaweedFS (S3-compatible object storage), rclone, content-addressable storage with SHA-256 dedupe |
| **Smart Preview proxy files** | should | medium | A lightweight (~2560px) lossy-compressed raw proxy stands in for the original, enabling full raw editing when the original is offline or too heavy to transfer; Classic syncs only these proxies to the cloud and they are exempt from quota. | LibRaw, Adobe DNG SDK (lossy DNG encode), libjxl (JPEG XL) or libavif as an open proxy format alternative |
| **Classic-to-cloud sync bridge** | wont | high | The desktop catalog app syncs only user-chosen collections (as proxies) upward while pulling full originals of anything added from mobile/web into a designated folder and a 'From Lightroom' collection group. Only one catalog can be bound to a cloud account at a time. | Same sync engine as cross-device sync plus per-collection sync flags |
| **Local cache and offline-availability controls** | could | medium | Cloud clients let users cap cache size, choose the cache disk, toggle 'keep a copy of all originals on this device', and pin individual albums for offline use on mobile. | LRU cache over object store, SQLite bookkeeping of pin/eviction state |
| **Local browse mode (edit in place, no upload)** | must | medium | The cloud desktop app can browse any local folder and edit raws where they sit, persisting edits to XMP sidecar files next to the originals instead of importing to the cloud. This is the core behavior a v1 desktop clone must nail. | exiv2 / exempi (XMP read-write), LibRaw / rawspeed (decode), darktable & RawTherapee XMP-sidecar conventions as prior art, efsw or watchdog (folder watching) |
| **Catalog migration / import from Lightroom Classic** | should | high | A guided tool ingests an existing Classic catalog — photos, edits, keywords, collections, stars and flags — into the new library in one pass. For a clone, importing real .lrcat files is a major adoption lever since they are plain SQLite. | SQLite (reads .lrcat directly), ExifTool, community reverse-engineering of Lightroom develop-settings XMP (crs: namespace) |
| **Mobile editing apps (iOS/Android) with near desktop parity** | wont | very-high | Phone and tablet apps offer the full raw editing pipeline — light/color panels, tone curve, AI masking, healing, geometry — on synced or on-device photos, with premium features gated by subscription. | Flutter or React Native shell, LibRaw via NDK, GPU pipelines (Metal / Vulkan / GPUImage), libultrahdr |
| **In-app pro camera with raw DNG and HDR capture** | wont | high | The mobile camera shoots DNG with manual ISO/shutter/WB/focus control and an HDR mode that brackets, aligns, deghosts, and merges exposures into a single 32-bit raw DNG that feeds straight into the synced library. | CameraX / Camera2 (Android), AVFoundation (iOS), HDRMerge (open-source raw exposure fusion), OpenCV alignment/deghosting |
| **Automatic camera-roll backup (auto-add)** | wont | medium | Mobile apps can watch the device photo library and silently import/upload new captures in the background, turning the service into an automatic photo backup. | PhotoKit / MediaStore APIs, Immich mobile app as open-source reference implementation |
| **Browser-based editor (Lightroom on the web)** | wont | very-high | A full web client at a hosted URL can browse the library, run real raw edits (including AI masking and compare-with-original view), manage albums, and drive all sharing features with no install. | WebAssembly builds of LibRaw, WebGPU / WebGL2 render pipeline, wasm-vips, PhotoPrism web UI as prior art |
| **Public link and QR-code album sharing with gallery theming** | could | medium | Any album can be published as a web gallery reachable by unique URL or QR code, with owner-chosen appearance (grid/theme, title, author) and toggles for downloads and metadata display. | Static gallery generators (Thumbsup, Sigal) as reference, PhotoSwipe / lightGallery, qrcode libraries |
| **Invite-based collaboration with permission tiers** | wont | high | Shared albums can be restricted to invited emails, each granted 'can view', 'can contribute' (add photos), or 'can edit' (adjust photos) rights, enabling multi-photographer group albums like a wedding pool. | Keycloak or Ory (identity), Casbin (RBAC policies), Immich shared-album model as reference |
| **Comments, favorites, and review notifications** | wont | medium | Viewers of a shared gallery can like and comment on individual photos and mark favorites; the owner sees activity in a notification bell across all apps, supporting client proofing/culling workflows. | Web push (web-push lib), Novu (open-source notification infrastructure), WebSockets |
| **AI semantic search of unkeyworded photos** | should | medium | Server-side ML (Adobe Sensei) invisibly tags every synced photo so free-text searches like 'dog on beach' work with zero manual keywording; tags are hidden and used only for retrieval, combined with metadata facets (camera, lens, location). A clone can run this fully locally with CLIP-class models. | OpenCLIP / SigLIP embeddings, FAISS or sqlite-vec (vector index), Immich smart search and PhotoPrism as proven open-source implementations |
| **Face detection and People view clustering** | should | medium | Faces are detected and clustered into unnamed people groups; naming one cluster labels the person library-wide and new imports are matched automatically. Classic runs this on-device, the cloud version server-side. | InsightFace (RetinaFace detection + ArcFace embeddings), dlib / facenet-pytorch, HDBSCAN clustering, Immich facial-recognition pipeline as reference |
| **Auto-curated 'best photos' selection** | could | medium | A one-click AI pass ranks an album by aesthetic/technical quality and surfaces the strongest images, with a slider controlling selectivity, aimed at rapid culling and gallery building. | NIMA aesthetic scoring models, LAION aesthetic predictor, pyIQA toolkit |
| **Assisted culling (focus, eyes, duplicates)** | could | high | Newer AI culling in Classic groups near-duplicate bursts and filters by subject-in-focus and eyes-in-focus/open, so a shoot can be reduced to keepers quickly. | OpenCV sharpness metrics, MediaPipe / dlib eye landmarks, imagededup (near-duplicate detection), perceptual hashing (pHash) |
| **Community feed with step-by-step edit replays** | wont | high | An in-app social feed (formerly 'Discover') where members publish finished photos whose full edit sequence can be replayed slider by slider, browsed by category, liked, and followed. | Edit recipes stored as ordered operation logs (enables replay for free), ActivityPub for a federated open-source take |
| **Save community edits as presets, and remixable photos** | wont | medium | Any shared community edit can be captured as a reusable preset in one tap, and authors can flag photos as 'remixable' so others publish derivative edits linked back to the original. | Serializable preset format (XMP-like or JSON), provenance links in the asset graph |
| **Follow system and personalized inspiration feed** | wont | high | Users follow photographers and get a 'For You' tab ranked by their likes, follows, and recent editing behavior, turning the editor into a lightweight photo social network. | Simple recommender (implicit-feedback matrix factorization, e.g. the `implicit` library) |
| **Premium curated preset packs** | could | low | Subscription-gated preset collections (portrait, travel, cinematic, film, etc.) refreshed with releases and installable across desktop, mobile, and web. A clone can ship free community packs instead. | XMP develop-preset parsing (exempi), existing CC0/free preset packs, darktable styles as a format model |
| **AI-recommended presets per photo** | wont | high | The app analyzes the current photo and suggests presets derived from how the community edited visually similar images, previewed as filmstrip thumbnails. | CLIP image similarity against a preset-tagged corpus |
| **Adaptive presets (mask-aware)** | could | high | Presets that first run AI segmentation (sky, subject, people/face regions, background) and apply their adjustments only inside the generated mask, so one preset adapts to each photo's content. | Segment Anything (SAM/SAM2), sky-segmentation models, MODNet / RMBG for subject-background separation |
| **Interactive in-app tutorials and guided edits** | could | medium | Step-by-step lessons run inside the editor on real sample photos, highlighting the exact slider to move at each step; paired with contextual how-to articles and videos in a Learn tab. | Guided-tour overlay patterns (driver.js style) reimplemented for desktop toolkit, tutorial scripts as declarative JSON step lists |
| **Versions: named and automatic edit snapshots** | must | low | Users can save named checkpoints of a photo's full edit state and the app also auto-creates rollback points over time; in the cloud ecosystem every version syncs to all devices (the Classic equivalents are Snapshots and the per-catalog History panel). | Edit-state rows in SQLite (a version is just a frozen copy of the recipe), darktable history-stack/snapshot design as prior art |
| **External-editor round-trip (Edit in Photoshop)** | must | low | One command renders the current edit to TIFF/PSD, opens it in Photoshop (or another editor), and on save the result returns to the library stacked beside the original with metadata carried over. | libtiff, psd_sdk (open-source PSD writer), file watchers for save-detection, GIMP/Krita as the open-source handoff targets |
| **Creative Cloud suite integration and pooled storage plans** | wont | high | The library participates in the wider Adobe account: shared cloud quota across apps, Firefly generative credits, Adobe Portfolio publishing of albums, and a single identity across Photoshop/Lightroom/mobile. | OIDC single sign-on (Keycloak), S3 quota accounting |
| **Lua plugin SDK (Classic-style extensibility)** | should | high | Classic exposes a documented Lua API where a plugin (declared by an Info.lua manifest) can add export/publish destinations, custom metadata fields and tagsets, library menu commands, dialog UIs, and web gallery engines — the foundation of the third-party ecosystem. | Lua 5.4 / LuaJIT embedding, sol2 (C++ Lua binding), alternatively Extism or QuickJS for a WASM/JS plugin runtime |
| **Publish services (two-way gallery sync to external sites)** | could | medium | Beyond one-shot export, a publish collection maintains an ongoing link to a destination (Flickr, SmugMug, hard drive, etc.): new photos upload, edited ones are flagged for republish, and removals propagate. | Per-service adapters over OAuth APIs, state table tracking published/modified/deleted status |
| **Third-party plugin ecosystem compatibility** | wont | very-high | A rich commercial plugin economy exists on the Classic SDK — Any Vision (Gemini/Cloud-Vision keywording and captioning), Negative Lab Pro (color-negative film inversion), LR/Mogrify 2 (export borders/watermarks), Excire (local AI search), jf publish plugins. Running these unmodified would require reimplementing large parts of Adobe's Lua namespace surface. | Adobe's public SDK docs enumerate the required Lr* namespaces, clean-room shim layer over the clone's own plugin API |
| **Public REST API for the photo service** | could | high | Adobe exposes lr.adobe.io to registered partners: OAuth 2.0 sign-in via its identity service, then JSON endpoints for accounts, catalogs, assets, albums, uploads, and renditions (up to 50 assets per album call), enabling camera-vendor auto-upload and lab integrations. | OpenAPI spec-first design (Adobe's spec is public on GitHub as a shape reference), FastAPI or Express, Ory Hydra (OAuth2), S3 presigned uploads |
| **Connected print/book/lab services** | wont | high | In-app 'connections' hand albums to third-party fulfillment partners (photo books, print labs) without manual export; Classic additionally has native Book (Blurb) and Print modules. | Partner-facing webhooks on top of the REST API |
| **Big-screen viewing app (Apple TV)** | wont | medium | A tvOS client browses the synced library and plays albums as slideshows on a television; view-only, no editing. | tvOS SDK, or a generic DLNA/Chromecast slideshow output as an open alternative |
| **Sync activity monitor and controls** | could | medium | A dedicated status view shows what is uploading/downloading per photo, overall progress, errors, and quota, with pause/resume and network preferences (e.g. metered-connection behavior). | Job-queue table with observable state (e.g. SQLite + event bus) |
| **Video in the synced library** | could | high | Videos upload, sync, and share alongside photos, with trim and a subset of color edits applicable in cloud clients; Classic can also apply limited develop settings to clips. | FFmpeg, mpv (embeddable playback), MLT framework for trim/edit |
