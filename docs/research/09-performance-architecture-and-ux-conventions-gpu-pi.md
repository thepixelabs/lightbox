# Performance architecture and UX conventions (GPU pipeline, caches/previews, catalog scale, background tasks, keyboard culling, UI layout, video, backup/migration)

Lightroom's performance story rests on three architectural pillars. First, a single-file SQLite catalog (.lrcat) holds every edit, rating, keyword, and history step as database records; Adobe requires it to live on a local (ideally NVMe) drive, and it demonstrably scales past a million images when maintained via the built-in Optimize Catalog routine (effectively a vacuum/reindex that users report shrinks files 10-15% and speeds queries). Second, a layered proxy system decouples the UI from expensive raw decodes: camera-embedded JPEGs for instant post-import culling, standard previews sized to the display, 1:1 previews for zooming, Smart Previews (small lossy-DNG proxies around 2560px that permit full offline editing), and a Camera Raw cache (default 5 GB, user-resizable/relocatable) holding partially-demosaiced raw state so the Develop module opens images quickly. Third, a tiered GPU strategy: display-only acceleration, full GPU image processing, GPU-accelerated export (roughly 2x faster on capable cards), and GPU inference for AI features (Denoise, Select Subject/Sky, Lens Blur), with hardware gating — DirectX 12/Metal required, and 8 GB VRAM (or 16 GB unified memory) recommended before the heaviest AI features feel usable. Long-running work (preview builds, sync, face recognition, reverse geocoding, exports) is surfaced through a stacked progress/activity model over the identity plate, with per-task cancel and pause controls.

On UX, Lightroom Classic established conventions the whole industry now copies: a task-based module bar (Library, Develop, Map, Book, Slideshow, Print, Web) with hideable modules; collapsible left/right panel groups with Solo mode, hover auto-reveal, Tab/Shift-Tab toggles, panel end-marks, and reorderable/hideable Develop panels; a persistent bottom filmstrip carrying selection state across modules; screen modes plus Lights Out dimming; and a secondary-display window offering Loupe (Normal/Live/Locked), Grid, Compare, and Survey on a second monitor. Its keyboard-culling grammar is de facto standard — P/X/U for pick/reject/unflag, 1-5 stars, 6-9 color labels, with Caps Lock (or Photo > Auto Advance) turning each keystroke into rate-and-advance — though notably Lightroom still offers no user-remappable shortcuts, only per-module cheat-sheet overlays. Video support is deliberately shallow: play/scrub, non-destructive trim of in/out points, capture-frame-to-JPEG, poster-frame selection, and a subset of develop adjustments, delegated to a DynamicLink/video cache subsystem.

The published pain points are a roadmap for Lightbox positioning: chronic complaints of laggy mask-heavy Develop sessions and 5-10 second stalls; a v15 Windows regression where each successive export got slower (up to 3x) until v15.2 fixed it — Puget Systems measured 49-59% benchmark improvements from that single fix, revealing how fragile the pipeline is; notoriously choppy video playback that degrades over a session; slideshow exports freezing at 1080p and GPU-related crashes that force users to disable acceleration entirely; slow module switching; import speeds far behind dedicated cullers like Photo Mechanic unless users discover the buried Embedded & Sidecar option (which cuts import time by ~90%); a strictly single-user, single-machine catalog with no network-drive support and no built-in multi-machine story short of paying for cloud sync; and background AI/sync tasks competing with interactive work. An open-source clone that ships embedded-preview culling by default, a crash-proof GPU pipeline with graceful CPU fallback, remappable shortcuts, and a catalog that tolerates network/multi-machine use would attack Lightroom's most-cited weaknesses directly.

## Feature inventory

| Feature | Priority | Complexity | Description | Building blocks |
|---|---|---|---|---|
| **Tiered GPU rendering pipeline** | must | very-high | Selectable acceleration levels — off, display-only, and full image processing (plus a custom mix) — with automatic capability detection, a status readout in preferences, and silent fallback to CPU when the driver misbehaves. Accelerates Develop rendering and Library grid/loupe/filmstrip drawing, with the biggest wins on 4K/5K displays. | wgpu, Vulkan + MoltenVK, Metal, OpenCL (darktable's pipeline as reference), vkdt (Vulkan raw pipeline reference), Halide, Skia |
| **GPU-accelerated export** | could | high | Optionally run the final render for export on the GPU, roughly halving export times on capable hardware; must coexist with interactive editing without starving the UI. | wgpu compute shaders, OpenCL, libjpeg-turbo, libvips |
| **VRAM-aware AI inference gating** | could | high | AI features (denoise, subject/sky masking, blur) run on the GPU when enough memory exists (Adobe recommends 8 GB dedicated VRAM or 16 GB unified) and are throttled, slowed, or disabled below that; inference shares the GPU with the render pipeline. | ONNX Runtime (DirectML/CoreML/TensorRT/CUDA execution providers), ncnn, Segment Anything (masking), NAFNet/Restormer-class denoisers |
| **Camera raw decode cache** | must | medium | A disk cache of partially processed raw data (Adobe's ACR cache, default 5 GB) so re-opening an image in the editor skips the expensive decode stages; user-resizable, relocatable to a fast drive, and purgeable. Users routinely raise it to 20 GB+ for a large Develop speedup. | LibRaw, rawspeed, rawler (Rust), zstd, LMDB or flat-file cache keyed by content hash |
| **Multi-tier preview pyramid** | must | high | Per-photo preview tiers — thumbnail, standard preview (sized/quality set per catalog), and full 1:1 — stored in a sidecar preview store (Lightroom's Previews.lrdata) so browsing never touches original raws. Standard preview dimensions can auto-match the display resolution. | libvips (pyramid generation), libjpeg-turbo, SQLite for preview index, AVIF/WebP as modern alternatives |
| **Embedded-preview instant culling** | must | medium | An import mode that reuses the camera's embedded JPEG (or sidecar preview) instead of rendering new previews, making photos browsable within seconds; community tests show it cuts import time by ~90% versus building standard previews. Lightroom can later replace these with its own renders in the background, and flags embedded previews in the UI since they don't reflect edit settings. | exiv2, ExifTool, LibRaw thumbnail extraction APIs |
| **Smart Preview proxy editing** | should | high | Compact lossy-DNG proxies (~2560px long edge; roughly 400 MB per 500 raws vs 14 GB of originals) generated on demand or at import, letting users make full edits while originals are on disconnected drives; edits reconcile automatically when originals reappear. Also usable as a deliberate performance mode (edit against the proxy even when originals are online). | Adobe DNG SDK (free but check license), dnglab (Rust, open source), LibRaw |
| **Preview retention policies and cache caps** | should | low | Catalog settings to auto-discard 1:1 previews after a chosen period (or never), pick standard-preview size/quality, cap the total preview-cache size (added in LrC v14), and manually discard previews for selected photos to reclaim disk. | LRU eviction over the preview index in SQLite |
| **Single-file catalog database at 100k+ scale** | must | high | All library state — folders, collections, metadata, edit parameters, history — lives in one SQLite database that stays responsive with hundreds of thousands (documented cases of 1M+) of photos; network drives are unsupported for the catalog to protect integrity, and a lock file enforces single-writer access. | SQLite (WAL mode), SQLite FTS5 for text search, proper indexing + prepared statements |
| **One-click catalog optimization** | should | low | A maintenance command (File > Optimize Catalog, also offered post-backup) that compacts and reindexes the database; commonly reported to shrink catalogs 10-15% and noticeably speed searches on 100k+ image libraries. | SQLite VACUUM / ANALYZE / REINDEX |
| **Exit-time catalog backup with integrity test** | must | medium | Scheduled backup prompts (on exit: daily/weekly/monthly/every time) that copy the catalog to a dated, zip-compressed folder, with checkboxes to test integrity before backup and optimize afterward; backups cover only the catalog, not previews or image files, and old backups accumulate until manually pruned. | SQLite Online Backup API, PRAGMA integrity_check / quick_check, libzip, zstd |
| **Corruption detection and repair workflow** | should | medium | Integrity verification at launch (hold a modifier key to force a check from the catalog picker), an automatic repair attempt when corruption is detected, and a guided restore-from-backup path when repair fails. | SQLite .recover command, PRAGMA integrity_check |
| **Non-destructive catalog upgrades and rename** | should | medium | Opening a catalog from an older app version copies it and migrates the schema, leaving the original untouched for rollback; since v14 the catalog can be renamed in-app with its preview and helper files renamed in lockstep on relaunch. | versioned SQLite schema migrations (refinery, sqlx-migrate, or hand-rolled) |
| **Unified background-task activity center** | must | medium | All long-running work — preview builds, imports, exports, metadata writes, face recognition, reverse geocoding, cloud sync — appears as stacked progress bars over the identity plate, each cancelable, with a disclosure to flip between concurrent tasks and pause buttons for the ongoing analysis services so they stop competing with interactive editing. | Tokio / async task runtime, Taskflow (C++), priority job queue with pause/resume semantics |
| **Demand-driven preview generation with virtualized grid** | must | high | The grid renders instantly from whatever preview tier exists and schedules missing renders visible-first, so scrolling a 100k-photo library never blocks; thumbnails upgrade in place as better previews finish. Bulk 'build standard/1:1 previews' commands exist for pre-rendering before a culling session. | virtualized list/grid widgets (Qt, Flutter, iced), libvips, thread-pool with cancellation on scroll |
| **One-key culling grammar with auto-advance** | must | low | P/X/U set pick/reject/unflag, 1-5 set star ratings, 6-9 set color labels, and with Caps Lock engaged (or Auto Advance enabled in the menu) every rating keystroke also moves to the next photo — collapsing cull-and-advance into a single keypress. Works in grid and loupe; the Library loupe is markedly faster than Develop for stepping through photos. | — |
| **Module-scoped shortcuts with cheat-sheet overlay** | must | medium | A deep, largely mnemonic shortcut set that changes meaning per module (G grid, E loupe, D develop, R crop...), each module offering an on-screen shortcut summary via Ctrl+/ (Cmd+/). Notably Lightroom offers no user remapping of shortcuts — a longstanding user request Lightbox could satisfy with a keymap editor. | declarative keymap/action registry (editor-style, e.g. VS Code keybinding model as design reference) |
| **Task-based module workspace** | must | medium | Top-level modules (Library, Develop, Map, Book, Slideshow, Print, Web) switch the entire workspace and panel set to one task; unused modules can be hidden from the picker. A v1 clone needs only Library + Develop equivalents but should preserve the mode-switch pattern and its shortcuts. | Qt/QML, Avalonia, Flutter desktop, egui/iced |
| **Collapsible panel framework with Solo mode** | must | medium | Left/right panel rails that collapse to edge strips with hover auto-reveal, Tab / Shift+Tab to hide side or all chrome, Solo mode that auto-closes other panels when one opens (a big perceived-speed win since closed panels don't recompute), decorative panel end-marks, and adjustable panel font size. | custom docking/accordion widgets in chosen UI toolkit |
| **Persistent cross-module filmstrip** | must | medium | A bottom thumbnail strip visible in every module that carries the current source and selection everywhere, showing flags/ratings badges, offering quick filters and a source breadcrumb/recent-sources menu, plus the buttons that spawn the secondary display. | shared selection model + the same virtualized thumbnail component as the grid |
| **Screen modes and Lights Out** | could | low | Cycled window states (normal, full screen with/without menu bar, full-screen preview on F) and the L-key Lights Dim/Lights Out modes that darken all chrome so only the photo remains for distraction-free evaluation. | — |
| **Secondary display window** | should | high | A second window (typically on a second monitor) showing Loupe in Normal/Live(hover-follows-mouse)/Locked modes, Grid, Compare, Survey, or slideshow — e.g. grid on one screen while editing full-screen on the other — with its own zoom control and a mini source/filter bar. Only one window may show the grid at a time. | multi-window support in the UI toolkit sharing one GPU context/catalog session |
| **Workspace customization and branding** | could | low | Reorder and hide Develop-module panels via a right-click customize dialog; replace the top-left identity plate with personal text or a logo graphic (also reused as branding in print/slideshow output); pick panel end-mark art and interface font size. | — |
| **Evaluation view modes (Compare, Survey, zoom conventions)** | should | medium | Compare view pits two candidates side-by-side with linked zoom/pan; Survey view lays out any N selected images and lets you eliminate losers one by one; Loupe zoom follows fit/fill/100%/custom presets with click-to-toggle and scrubby panning — conventions users' muscle memory expects. | shared tiled-image viewer component with synchronized viewports |
| **Basic video handling: play, trim, frame grab, poster** | could | high | Import and play common containers (MP4/MOV/AVI/AVCHD) with a scrub bar; non-destructively trim in/out points (applied only on export); capture the current frame as a JPEG; set any frame as the clip's poster/thumbnail; apply a limited subset of tone/color adjustments to clips. Deep video editing is explicitly out of scope in Lightroom. | FFmpeg, libmpv (embeddable playback), GStreamer |
| **Dedicated video cache with size cap** | could | low | A separate on-disk cache for decoded video/preview data with a user-set maximum size and purge control, so video work cannot swamp the image caches (Lightroom's DynamicLink-backed video cache; clearing it is a standard fix for choppy playback). | FFmpeg frame cache keyed by clip+timestamp |
| **Slideshow authoring and video export** | wont | medium | Template-driven slideshows with transitions, optional soundtrack, sync-slides-to-music, an 'impromptu slideshow' shortcut from any view, and export to MP4 (up to 1080p). Adobe forums document freezes on large 1080p exports and stutter between transitions — a low bar to clear. | FFmpeg (encode + crossfade filters) |
| **Parallel import pipeline with second-copy backup** | must | high | Import concurrently copies/moves files, writes catalog records, extracts or builds the chosen preview tier, applies metadata/develop presets, and can simultaneously duplicate incoming files to a second drive as an immediate backup; optional convert-to-DNG runs as a deferred stage. Card ingest speed and preview choice dominate perceived performance. | multi-threaded copy with checksums (xxHash), exiv2/ExifTool, dnglab for DNG conversion |
| **Progressive Develop loading** | should | medium | Opening a photo in the editor immediately shows the newest available preview with a 'Loading' badge, then swaps in the full raw render when the pipeline (fed by the raw cache) finishes — the UI never blanks while waiting for a decode. | staged render graph: preview tier -> cached half-processed raw -> full pipeline |
| **Multi-catalog session workflows** | could | medium | Export any selection as a standalone catalog (optionally with previews/smart previews and originals) for travel or per-job work, then merge back via import-from-catalog with conflict handling; recent-catalogs menu and a default-catalog preference manage switching. Adobe still recommends one master catalog since only one can be open at a time. | SQLite ATTACH-based copy/merge routines |
| **Pausable background analysis services** | could | high | Opt-in face detection and reverse-geocoding (GPS to place names) run as low-priority background services over the whole library, individually pausable from the activity center because they visibly steal CPU from editing. | OpenCV YuNet (detection), InsightFace/ArcFace (recognition), offline GeoNames dataset or self-hosted Nominatim |
| **Performance preferences panel** | must | low | One place to control the performance envelope: GPU mode selection with detected-hardware readout, camera-raw cache size/location/purge, video cache cap, preview-related toggles, and 'use smart previews instead of originals' — mirroring where Lightroom users expect these knobs. | — |
| **Cloud-tier local cache model (reference architecture)** | wont | very-high | The cloud-based Lightroom keeps originals in cloud storage with a size-capped local cache, optional 'store all originals locally' and 'store all smart previews locally' switches for offline editing, and background upload after import. Out of scope for a local-first v1 but the tiering model informs any future Lightbox sync server. | content-addressed store + LRU cache, rclone/S3-compatible backends, CRDT or op-log sync for edits |
